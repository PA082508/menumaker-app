## 0. Что подтвердилось до начала: формула экрана = формула SQL

Ручная сверка владельца шла по **Pre-K**, а не по Green Room: четыре пары чисел —
**29.06 = 27/31 · 30.06 = 23/26 · 01.07 = 24/27 · 02.07 = 27/31** — совпадают с Pre-K клетка в
клетку. Green Room в те же дни даёт 15/18 и 14/17. Комната названа не для придирки: дельта ниже
считается **по всем комнатам**, и знать, какая именно проверена рукой, важно.

Экранное правило (`reimbursableSlots`,
[MealCountPage.tsx:141-150](../../src/pages/meal-count/MealCountPage.tsx#L141-L150)) на живом
наборе из четырёх слотов даёт **ровно** `b*(1-(b*l*s)) + a + l + s` — формулу
`compute_monthly_claim`. Расхождений по приёмам нет ни в одном дне ни одной комнаты Pearl.

⚠️ **Оговорка, снимающая кажущееся совпадение:** равенство держится потому, что
`pm_snack`/`evening_snack` **не отмечены ни разу** (0 отметок во всех центрах). Экран этих двух
слотов не знает вовсе (`active_slots` = breakfast/am_snack/lunch/supper), а SQL их считает. Первая
же отметка PM Snack разведёт счётчики без всякой правки кода.

### Откуда берётся невидимое — три механизма, все измерены

**(1) Ребёнок сменил комнату — строка осталась в СТАРОЙ.**
`meal_week_records` держит `classroom_id` той комнаты, где галочку ставили. Экран строит список из
`v_meal_grid` по **текущей** `roster.classroom_id`. Ребёнок ушёл в другую комнату — старая строка
не показывается **никому и никогда**, а в клейм входит. Основная доля невидимого.

**(2) Ребёнок выбыл или помечен неактивным — прошлое исчезает задним числом.**
`v_meal_grid` фильтрует `COALESCE(r.is_active, true)`. Снятие флага гасит **все** прошлые недели
ребёнка на экране; в клейме они остаются. Pearl июнь: 16 возмещаемых приёмов.

**(3) Один ребёнок отмечен в ДВУХ комнатах в ОДИН день.** Не расхождение счётчиков, а порча
данных, которую **ни один из них не ловит**: SQL складывает обе строки, экран показывает каждую
комнату отдельно и по-своему прав.

### Два наблюдения о категориях — не про наборы строк, но про то же число

- **5 из 61** едоков Pearl **не имеют ни одной записи `income_eligibility`**. `compute_monthly_claim`
  молча зовёт их `'P'` (paid). Экран о категории не говорит вовсе — спорить не с чем, но и увидеть
  нечего. Ещё **2** имеют F/R с `frp_expires` раньше июня — тоже падают в `'P'`.
- `meal_count_settings.claim_excluded_slot = 'breakfast'` **не читает никто**: ни экран, ни
  `compute_monthly_claim`. Настройка стоит у всех четырёх центров и ни на что не влияет.

### Ответ на вопрос «есть ли у нас два счётчика»

**Есть.** По арифметике они согласны, по составу строк — нет, и разница не косметическая:
**212 возмещаемых приёмов за июнь только по Pearl, 1034 по Ridge.** Блокировка не снимается.

⭐ **Сформулировано как правило:** экран считает **по сегодняшнему ростеру**, клейм — **по строкам
недели**. Пока ростер меняется (перевод, выбытие), эти два множества расходятся тем сильнее, чем
дальше неделя в прошлом. Это не «ошибка в фильтре», это **разные опоры**.

## 3. ЧТО ОТКАЗЫВАЕТ ЗАПИСИ В ПРАЗДНИК НИЖЕ ЭКРАНА — НИЧЕГО

Ожидание владельца подтвердилось полностью.

| Слой | Спрашивает ли про `holidays` |
|---|---|
| `menumaker.sync_meal_marks(jsonb)` — **единственный писатель** галочек | **НЕТ.** Тело прочитано целиком: белый список из 30 имён колонок, `insert … on conflict do update set <колонка>`, вставка в журнал `meal_count_marks`. Слова `holiday` в теле нет |
| RLS на `meal_week_records` — 3 политики: `auth_manage` (`true`/`true`), `org_isolation`, `module_cacfp_active` | **НЕТ.** Ни одна не упоминает ни праздники, ни дату, ни статус |
| Триггер `trg_guard_meal_approval` → `guard_meal_approval()` | **НЕТ.** Стережёт **только** `director_initials` / `director_signed_at`. Клетки, статус и календарь ему безразличны |
| `menumaker.center_holidays` | пустая таблица, 0 строк, писателей нет |

🔴 **Называю прямо, как назван замок:** **правило «в праздник не отмечают» живёт ТОЛЬКО маской на
экране.** Любой путь мимо экрана — прямой вызов RPC, старая вкладка с уже загруженной неделей,
очередь IndexedDB, синхронизировавшаяся после того, как день объявили праздником, — **запишет
галочку 03.07 и не встретит ни одного отказа.** То, что таких отметок сегодня нет, — свойство
дисциплины людей, а не свойство системы.

⚠️ **Очередь IndexedDB — не теоретический путь.** Отметка ставится офлайн и доезжает позже
(`enqueueMark` → `sync_meal_marks`). Маска считалась **в момент показа экрана**; правило,
объявленное после, к уже поставленной отметке не применяется никем.

## 4. ЗНАЕТ ЛИ МАСКА ПРО SHORT DAY — ЗНАЕТ, НО СЕГОДНЯ МОЛЧИТ

**Код знает.** [MealCountPage.tsx:487-495](../../src/pages/meal-count/MealCountPage.tsx#L487-L495):

```ts
if (h?.type === "short_day" && h.close_time) {
  const start = slotStart[slot];
  return !!start && start >= h.close_time.slice(0, 5);   // гасится ТОЛЬКО поздний слот
}
```

Это ровно клеточное правило раздела 3 спеки: полный праздник гасит день целиком, `short_day` — лишь
те приёмы, что **начинаются в/после** времени закрытия. Клетка подписывается «Short Day · closes HH:MM».

**Но на живых данных ветка не срабатывает ни разу:** у всех **6** строк `short_day`
(24.12 и 31.12 × 3 центра) **`close_time = NULL`** → условие ложно → **не гасится ничего**.
Сокращённый день сегодня выглядит как обычный.

**Опора для маски готова:** `meal_schedule.start_time` заполнено практически везде — Pearl 40 строк
на 10 комнат (4 из 4 слотов), Ridge 44 на 11, Highland 32 на 8 (не хватает одного `supper`),
ZZ Demo — 0 строк. Как только `close_time` появится, маска заработает без правки кода.

⚠️ **Второй край того же:** пустой `start_time` даёт `!!start === false` → слот **не гасится**.
Отсутствие расписания читается как «работаем», а не как «неизвестно».

### Как посчитано «до»

Дельта не угадана: `meal_count_marks` — журнал точки обслуживания — за 30.07 несёт **315 нажатий
по 303 клеткам** недели 29.06 (Pearl, 53 ребёнка). Экранная кнопка **переключает**
(`next = current ? 0 : 1`), поэтому **первое** сегодняшнее нажатие по клетке восстанавливает её
прежнее значение однозначно: `было = 1 − значение первого нажатия`. Клеток с повторным нажатием —
9, они разобраны по времени.

**Результат восстановления: до сегодняшнего ввода 29.06 и 30.06 были ПУСТЫ ЦЕЛИКОМ.** Ни одной
галочки ни в одной комнате. Остальные июньские недели (01.06 · 08.06 · 15.06 · 22.06) сегодня **не
трогали вовсе** — их `updated_at` старше. Значит вся июньская дельта = сегодняшний ввод по двум
дням.
