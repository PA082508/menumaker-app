# Разделение PIN-возможностей и реестр PIN-точек (канон владельца 07.08; бумага)

Спека механизма PIN. Отсюда же берёт правило Payroll Gate
([`2026-08-07-staff-hr-vault.md`](2026-08-07-staff-hr-vault.md), пункт 2) и правка отметок
питания задним числом ([`2026-08-07-meal-marks-amendment.md`](2026-08-07-meal-marks-amendment.md)).

## Канон, из которого всё следует

**PIN не повышает роль. PIN подтверждает ЛИЧНОСТЬ ВНУТРИ роли.**

Четыре цифры — это подпись, а не ключ от чужой двери. Директорский PIN не делает человека
владельцем; учительский не делает директором. Если поверхность требует прав, которых у роли нет,
**PIN не помогает** — он отвечает на вопрос «кто это», а не «можно ли».

Отсюда прямое следствие для сервера: **проверка «роль + точка» идёт ДО проверки PIN.**
Сначала сервер решает, положено ли этой роли это действие в этом центре; и только потом спрашивает
подпись. Обратный порядок превращает PIN в эскалацию привилегий — вводом четырёх цифр человек
добирался бы туда, куда ему не положено по роли.

## Реестр PIN-точек

Реестр — не украшение: **точка, которой нет в реестре, не имеет права спрашивать PIN.** Колонки
ровно три и все обязательны.

| действие | кому доступно (роль + центровой скоуп) | след |
|---|---|---|
| **ЖИВОЕ СЕГОДНЯ** | | |
| подтвердить передачу ребёнка (`safepass_confirm_handoff`) | сотрудник комнаты; скоуп — центр **токена устройства**, не сессии | запись передачи с именем подтвердившего |
| чек-ин / чек-аут сотрудника (`safepass_staff_check_in` / `_check_out`) | сотрудник центра токена | `staff_time_events` |
| погасить одноразовый код доверенного (`safepass_redeem_temp_code`) | сотрудник у двери | запись выдачи |
| рейс транспорта: открыть · тап · дописать ребёнка · лист · закрыть (`safepass_driver_*`) | водитель центра токена | запись рейса |
| завести PIN сотруднику (`safepass_set_staff_pin`) | **директор своего центра**; владельческая ветка `is_org_owner` — аварийный запас | `pin_set_by` / `pin_set_at` честно показывают исключение |
| спросить статус PIN (`safepass_staff_pin_status`) | тот же роль-гейт и охват, что у записи | — |
| **ЗАКАЗАНО, НЕ ПОСТРОЕНО** | | |
| вход в оболочку `/teacher` | сотрудник центра токена | именные отметки питания |
| правка отметки питания задним числом | **директор своего центра** | штамп `amended after service` в самой записи + видимость в недельном подтверждении |
| ручная выдача ребёнка (без родительского тапа) | **директор своего центра** | причина словами + запись |
| одноразовый код доверенного — выпуск | **директор своего центра** | кем и кому выдан |
| настройки своих комнат | **директор своего центра** | журнал настройки |
| **отметка отсутствия сотрудника** (`sick` · `no-show` · `approved leave`) | **директор своего центра** | тип причины отдельным полем (вход будущих начислений) + полоса «absent» + пересчёт линии потребности; день **без часов** |
| **задний check-in за забывшего** | **директор своего центра** | причина словами + штамп `amended` в самой записи; правка меняет часы → тот же вычислитель и та же неделя подтверждения |
| показать зарплатные поля орг-персонала | **сам человек** (свой PIN); правка — по слову владельца | след просмотра — предложить в показе |

Две последние строки — заказ 07.08 «утро без учителя»; их формулы и то, что видит человек, —
в [`2026-08-06-teacher-app-v1.md`](2026-08-06-teacher-app-v1.md), раздел директорских PIN-точек.
**В v1 понедельника они не входят.**

**Директорский PIN = директорский класс исправлений В СВОЁМ ЦЕНТРЕ.** Всё, что выше этого класса
(орг-уровень, чужой центр, деньги чужого человека), открывается **только соответствующим PIN'ом —
владельца или Татьяны — и только в их клетках реестра**. «Директор с PIN» и «владелец с PIN» —
две разные строки таблицы, а не одна с разной силой.

## Список возможностей — КОНФИГ владельца, а не хардкод

Кто что может — **настройка**, живущая данными: строка реестра, а не `if (role === 'director')`,
разбросанный по коду. Причина та же, что у порога «3 месяца» в holiday pay: правило меняется
жизнью центра, а перевыкладка ради переезда одной строки — плохой обмен. Реестр читают **и сервер,
и экран**, чтобы «кнопка есть» и «действие пройдёт» не разошлись.

## Что это меняет в уже написанных бумагах

- **Payroll Gate, пункт (в)** («кто вправе править payroll орг-персонала») перестаёт быть открытым
  вопросом механики: право на правку — у **роли**, PIN лишь подтверждает, что за экраном тот
  человек. Вопрос владельцу сужается до одной клетки реестра.
- **Правка отметок питания** получает своё место в реестре — директорский класс, свой центр, след
  обязателен. Формула остаётся как есть, реестр отвечает «кому».
- **Замер 07.08 в помощь:** `pin_hash` / `pin_set_at` / `pin_set_by` **закрыты колоночным грантом**
  (403 обычной сессии) — механизм «поле не отдаётся, отвечает только DEFINER-функция» уже стоит и
  проверен на PIN; деньгам он и предлагается.

## Открытое (в показ)

- **Порядок проверки на живых RPC.** Сегодня функции спрашивают хэш PIN и опознают человека внутри
  центра токена; ОТДЕЛЬНОЙ проверки «этой роли эта точка положена» в них нет — она подразумевается
  тем, что точка вообще существует. Реестр требует сделать её явной. Замер перед стройкой: какие
  из живых функций нужно дополнить и что это стоит.
- Где живёт реестр (таблица в БД против файла конфигурации), кто его правит и как выглядит его
  read-back — вопросы показа, ответ владельца.
