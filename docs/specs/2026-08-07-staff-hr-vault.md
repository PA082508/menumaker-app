# Staff / HR — копилка (бумага; ничего не строится без слова)

Складываем сюда всё, что относится к сотруднику как к нанятому человеку, а не к его работе в
комнате. Каждый пункт — заказ владельца с датой. Стройка по слову, поштучно.

**Канон, который держит всю копилку** ([`../DECISIONS.md`](../DECISIONS.md), 07.08):
персоналу обещаем **отражение отработанных часов, не прозрачность оплаты**. Подсчёт часов —
это факт тапов; любые деньги — **слой начислений**, и он появляется в текстах и в UI только
вместе с собой, не раньше.

## 1 · HOLIDAY PAY + ПОРОГ СТАЖА (заказ 07.08)

**Правило владельца:** праздничные **не оплачиваются в первые 3 месяца** работы.

Разделение, без которого пункт разъедется:
- **часы** = факт тапов (`staff_time_events`) — уже есть и ничего про деньги не знает;
- **оплачиваемый праздник** = слой **НАЧИСЛЕНИЙ** — его нет.

Что нужно слою:
| вход | где лежит сегодня | состояние |
|---|---|---|
| `hire_date` | карточка сотрудника, `menumaker.staff.hire_date` | колонка есть; **у части людей пусто** — замерять перед стройкой |
| календарь праздников | Settings → Schedule & Holidays | есть |
| порог «≥3 мес» | — | **конфиг политики, не хардкод**: правило меняется, а перевыкладка ради числа — плохой обмен |

**Выход:** зарплатный отчёт «фактические часы + оплачиваемые праздники при выслуге».
**Стык отметить:** Daily Time Log и экспорт в QuickBooks — праздничные часы не должны попасть в
фактические, иначе один и тот же день уедет дважды.

**Замер источника при заходе в слой** (заказ 07.08): карточка **уже несёт** блок Benefits
Eligibility — «months worked · hired · Full-time: No — 32h+ required for holiday/vacation pay».
Правило «3 месяца» ложится **рядом с этим признаком**, а не отдельным углом. Перед стройкой —
измерить, откуда блок берёт свои числа: если он считает `months worked` сам, вычислителей станет
два, и разойдутся они ровно так же, как итог часов в Work Schedule (см. пункт 3).

## 2 · PAYROLL PRIVACY GATE (org-level) — заказ 07.08

**Спека + показ — после показа инбокс-папок. Стройка по слову. Не блокер понедельника.**

Недельный оклад и годовой эквивалент **административного** персонала видимы **только под ПИНом
самого человека**.

- **(а) Маска.** Payroll-блок карточек `is_org_level` замаскирован **любому** зрителю, включая
  других админов.
- **(б) Замок — СЕРВЕРНЫЙ.** Поля не отдаются без верификации: RPC «проверь свой DOOR PIN → отдай
  цифры на время, с таймаутом». **UI-маска без серверного замка не считается.**
- **(в) В показ:** кто вправе **править** payroll орг-персонала (предположение — владелец; слово
  его) · величина таймаута · след просмотров (предложить).
- **(г) Замер всех путей утечки** зарплатных полей org-staff: карточка · Daily Time Log ·
  экспорты — всё под тот же замок.
- **(д) Обычный персонал не трогается.** Черта — по `is_org_level`.

### Замер уже сделан (читка-после 07.08) — пункт (б) не гипотетический

`GET /rest/v1/staff?select=id,hourly_rate` под **обычной** сессией `authenticated` возвращает
**200**. Колонка `hourly_rate` читается кем угодно, кто вошёл в приложение; прячет её сегодня
только UI. Для сравнения — `pin_set_at`, `pin_set_by` и `pin_hash` **закрыты колоночным грантом**
и дают 403 на том же запросе. То есть механизм, который нужен пункту (б), в проекте **уже
применён к PIN** и просто не применён к деньгам.

На 07.08: активных сотрудников 73, из них `is_org_level` — 6; непустой `hourly_rate` — у 2 человек
(оба центровые, не орг-уровень). Цифры окладов здесь не приводятся намеренно.

Отсюда рабочая гипотеза для спеки: замок = **колоночный REVOKE** + DEFINER-RPC, отдающая поля
после проверки собственного PIN. Это не новый механизм, а тот же, что уже стоит на PIN.

## 3 · ДВА ВЫЧИСЛИТЕЛЯ ЧАСОВ — мини-фикс в окно белой Cancel (заказ 07.08)

**Что видно человеку** (фото владельца, живой Work Schedule): строка Mon 06:30–15:30 с обедом
12:00–13:00 показывает **Hours 8.0**, а **Total weekly = 8.5h**. Итог считает по legacy
`break_minutes` (−0.5 ч), строка — по интервалу обеда (−1 ч).

**Замер 07.08.** В `staff_schedules` после сборки Work Schedule v2 (`2fb145b`, 06.08) появилось
**10 строк, и все 10 несут ОБА представления обеда сразу** — `break_start`/`break_end` **и**
`break_minutes`. Строк только с интервалом — 0, только с legacy — 0. То есть расхождение не
случайное и воспроизводится на каждой новой строке: два поля, два читателя, два ответа.

**Лечение:** `Total` = **сумма строчных `Hours`**. Единственный вычислитель — строка; итог не
считает сам ничего.

**Проба:** строки с интервалом · строки legacy · смесь — итог всегда равен сумме видимых `Hours`.
**Read-back на живом той же карточкой** — ожидается **8.0** при одном понедельнике.
