## 0. Заказ в одну фразу

При кампании обновления **ручной осмотр только там, где нужна подпись директора**.
Всё остальное — авто в БД, со знанием админа.

Из этого следует инверсия сегодняшней логики. Сейчас Inbox — это очередь **всего**, что
пришло (`status='pending'`, [EnrollmentInboxPage.tsx:143](../../src/pages/enrollment/EnrollmentInboxPage.tsx#L143)), и человек глазами
перебирает каждую строку. При 150 продлениях эта очередь перестаёт быть сигналом.
Контур должен оставить в очереди **только то, что требует человека**, а остальное
провести в БД и показать как факт, а не как задачу.

## 1. Главный дом контура = тетрадь ENROLLMENT

Renewal Tracker, очередь «Awaiting director signature», расхождения и «кому ещё послать»
живут **внутри Enrollment**. Не на аватарках, не отдельной страницей.

### 1.1. Красная цифра = только actionable

Сегодня цифра считается в двух местах ad-hoc и означает «сколько pending»
([CenterRosterPage.tsx:239](../../src/pages/children/CenterRosterPage.tsx#L239), [StaffPage.tsx:53](../../src/pages/staff/StaffPage.tsx#L53)).

**Новое определение — цифра считает только то, что ждёт человека:**

| Входит в цифру | Не входит |
|---|---|
| ждёт подписи директора (`requires_countersign=director`) | авто-филенное (`received`) |
| расхождение при матчинге / не сматчено | успешно продлённое |
| new enrollment (не renewal) | — |
| *(опционально, флагом)* «не отправлено» | — |

Если авто-филенное попадёт в цифру, сигнал снова станет «150» и умрёт. Это главное
требование к контуру, а не деталь.

Авто-филенное **видно** — внутри трекера, со статусом `received`. Видно ≠ actionable.

**Инженерная заметка:** цифру надо считать один раз и в одном месте. Сегодня она
дублируется двумя запросами `count:'exact', head:true` без refetch после approve.
Кандидат — блок в `refresh_action_items`, где уже есть severity/dismiss/snooze
([ActionItemsWidget.tsx:49](../../src/components/dashboard/ActionItemsWidget.tsx#L49)), но enrollment там сейчас не представлен.
Решение — при утверждении.

## 2. Состав контура

### (a) Реестровый признак `auto_file`

Новое поле в записи реестра `enroll-registry.json` (schema 2).

```jsonc
"iea": {
  "auto_file": true,          // сабмит, сматченный с ребёнком ростера + валидный → авто-файл
  "expiryMonths": 12,         // уже есть — цикл продления
  "signer": "parent",         // уже есть
  ...
}
```

**Правило авто-файла — все три условия одновременно:**

1. это **renewal** (сабмит однозначно сматчен с ребёнком активного ростера — см. §2e), **и**
2. валидация чистая (🟢 по `validateSubmission`, без errors), **и**
3. форма несёт `auto_file: true` **и** не требует контрподписи (§2b).

→ пишем в БД, статус **`received`**, **без ручного Approve**.

**Всё остальное — в ручную очередь как сейчас:**
- new enrollment (нет матча с ростером),
- любое расхождение (см. §2e),
- 🟡/🔴 валидация,
- формы без `auto_file`.

> **Что НЕ авто-филится никогда, независимо от флага:** определение F/R/P
> (`approveIea` → `roster.frp` + `income_eligibility`). Это claim-доказательство и оно
> под claim-мостом до 1 октября. IEA может авто-филиться как *документ получен*, но
> **определение F/R/P остаётся ручным** до отдельного решения. Это граница, которую
> контур не переходит.

**Миграция статусов.** `status` в БД ограничен CHECK-ом
`('pending','approved','rejected')` ([20260703_enrollment_submissions.sql:32](../../supabase/migrations/20260703_enrollment_submissions.sql#L32)).
`received` требует миграции + правки `.eq('status','pending')` в Inbox и в обеих
badge-запросах. Миграция — prepare+go, не автоматом.

### (b) `requires_countersign` — всегда в рабочую очередь

Нового поля в реестре **нет** (есть `signer: 'parent' | 'physician'`).

```jsonc
"requires_countersign": "director"   // новое; null | "director" | "staff"
```

Форма с `requires_countersign: "director"` **никогда** не авто-филится, даже при
`auto_file: true` и чистой валидации. Она идёт в очередь с фильтром
**«Awaiting director signature» — включённым по умолчанию**.

Известные кандидаты: Transition into program (центр-сторона = директор на Inbox review),
Release Authorization v2. Точный список — при утверждении.

Сегодня в Inbox **нет ни одной вкладки/фильтра** — есть только поиск по имени и
URL-параметр `?from=staff|children`. Фильтры-вкладки строятся с нуля.

### (c) Renewal Tracker (MVP)

Внутри Enrollment. По семьям/детям, колонки = стадии:

| Стадия | Источник истины |
|---|---|
| **Отправлено** (prefill выдан) | нужна новая таблица — сегодня факт отправки нигде не фиксируется |
| **Заполнено** | `enrollment_submissions.created_at` |
| **В БД** | `status='received'` (авто) или `'approved'` (ручное) |
| **Ждёт подписи** | `requires_countersign` + подписи нет |
| **Готово** | подписано / продление закрыто |
| **Кому ещё послать** | ростер минус «отправлено» — колонка-остаток |

Последняя колонка — **самая ценная для админа** и единственная, которую нельзя
получить из существующих таблиц: нужен реестр «кому что выдано». Без него кампания
идёт вслепую.

**Это же — ответ на «кому ещё послать»**: не отдельный экран, а колонка трекера.

### (d) Бейдж на аватаре — вторичный слой

⏳ = отправлено/ждём · ✓ = обновлено. Виден при открытии класса.
**Повседневный сигнал остаётся за красной цифрой Enrollment** — бейдж её не заменяет.

`Avatar.tsx` не имеет слота под бейдж, но ростер уже кладёт оверлей снаружи —
`position:relative` обёртка + абсолютный кружок ([CenterRosterPage.tsx:698](../../src/pages/children/CenterRosterPage.tsx#L698)).
**Важно: правый нижний угол занят точкой присутствия** — renewal-бейдж идёт в правый
верхний. Либо расширить `Avatar` необязательным `badge?: ReactNode` (безопасно: все
существующие вызовы передают только `name`/`size`/`path`/`fontSize`).

### (e) Опознание renewal → ребёнок ✅ ИСПРАВЛЕНО 2026-07-16

> **Правило изменено: renewal опознаётся по ТОКЕНУ ВЫДАЧИ, а не по имени.**
> Прежняя редакция этого раздела (матчинг по имени через `matchRoster`) была **неверна**,
> и написал её я. Ниже — почему, чтобы никто не вернул её обратно.

#### Почему матчинг по имени не работает для renewal

Замер по живым строкам 2026-07-16:

| Факт | Следствие |
|---|---|
| `parent_consent` **не несёт DOB** (`form_data ? 'birthdate'` → false) | мягкая ветка `matchRoster` **не может сработать** — она включается только когда DOB подтверждает |
| остаётся единственный путь — **точное** совпадение имени | родитель печатает имя **от руки** |
| единственное живое согласие: на форме «Izabella Rodriguez», в ростере «Rodriguez-Texidor Izabella» | **точных совпадений: 0** |

Итого: авто-файл по имени не сработал бы **ни на одной живой строке**. А ослабить правило
нельзя — это положит документ в чужую карточку, единственный исход **хуже** очереди.

#### Ответ был в конструкции контура

**Renewal — это то, что ВЫДАНО.** `prefill_tokens.token` уезжает в prefill-ссылке (`?t=`) и
возвращается с сабмитом. **Не нужно вычислять, кто это, — мы уже знаем.** Именно факт
выдачи и делает сабмит продлением; имя тут вообще ни при чём.

| Что пришло | Действие |
|---|---|
| **токен есть**, найден в `prefill_tokens`, не истёк, центр совпал, **DOB ребёнка совпал** (§2e-2) | **renewal → авто-файл** (при прочих условиях §2a) |
| токен ок, но **DOB не совпал** | **в ручную очередь**, причина `token DOB mismatch` (§2e-2) |
| токен есть, но не найден / **истёк** | **в ручную очередь** — истёкший токен не доказательство личности |

| токен есть, но центр токена ≠ центр сабмита | **в ручную очередь** |
| **токена нет** | это **не renewal**, а walk-in → §2e-1 |

#### §2e-2. Дыра пересылки токена → DOB-подтверждение (решение 2026-07-18) — 🚧 ГЕЙТ

Токен **не одноразовый** и живёт ~30 дней (prefill-engine §1). Валидную ссылку `?t=`
можно **переслать из рук в руки** — тогда токен «есть, найден, не истёк, центр совпал»,
но сабмит пришёл не от той семьи. Один валидный токен ⇒ авто-файл в **чужую** карточку —
ровно тот исход, что хуже очереди. Токена самого по себе **недостаточно**.

**Решение (Николай):** на токеновом пути — **второй фактор, дата рождения ребёнка**.

- **Форма** (Pages-репо, `pa082508.github.io`): при наличии токена показать поле
  «дата рождения ребёнка»; токен эхом уходит с сабмитом как сейчас.
- **Edge** (`enrollment-autofile`): сверить присланный DOB с `roster.birthday`
  токенового ребёнка (`prefill_tokens.child_id`):
  - совпало → renewal → авто-файл (при прочих условиях §2a);
  - **не совпало → ручная очередь, причина `token DOB mismatch`** — не гадаем, решает человек.

**🚧 ГЕЙТ: `commit:true` авто-файла НЕ включается до этого захода.** До поставки
DOB-сверки авто-файл остаётся в dry-run **независимо** от прочих условий §2a. Это
предусловие безопасности, а не часть §2a. Смета (CC 2026-07-17): edge ~1 заход +
юнит-тесты (в `menumaker-app`, не блокирован); форма ~0.5 (блокирована клоном Pages);
эта правка спеки — сделано.

#### §2e-1. Walk-in (токена нет)

Сабмит без токена никто не выдавал: это новое зачисление, приход с улицы или ссылка,
переданная из рук в руки. **Имя пробуем из вежливости, но результат почти всегда один:**

| Результат | Действие |
|---|---|
| ровно 1 точное попадание имени | **⏳ ОТКРЫТО — см. §6 вопрос 1.** Пока: в ручную очередь |
| 2+ кандидата | **в ручную очередь**, показать всех |
| 0 кандидатов | **в ручную очередь** (new enrollment) |
| DOB противоречит | **никогда не матч** |

**Правило неизменно: при любой неоднозначности — человек. Не гадать.**

#### Что осталось верным из прежней редакции

`matchRoster` **не выбрасывается** — он остаётся для walk-in и для ручного review, где
человек видит кандидатов и решает сам. Его правила (противоречащий DOB исключает всегда;
мягкое совпадение только при подтверждающем DOB; `loadCenterRoster` включает неактивных,
чтобы вернувшийся ребёнок реактивировался, а не дублировался) — в силе.

**Издание/фискальный год** берётся из **строки издания формы**, не из арифметики по
датам (`parseIeaFiscalYear`, [enrollmentApprove.ts:93](../../src/lib/enrollmentApprove.ts#L93)). Продлить = указать на новое
издание (`current` в реестре), и FY выпадает из токена сам. Это же согласуется с
queued-спекой «period-effective references».

#### Следствие для порядка работ

Авто-файл заработает **только когда пойдут выдачи с токеном**. На pre-token сабмитах он
честно не сделает ничего — это не дефект, а отказ гадать. Значит выдача
prefill идут **раньше** первого `commit:true`.

## 3. Коммерческое применение

Этот же контур — **zero-migration onboarding**.

Когда клиент переходит на платформу, у него нет истории в нашей БД: нужно массово
собрать актуальные документы по всему ростеру. Это ровно кампания продления, только
стартовое состояние — «не отправлено» у всех.

Отсюда проектные требования:

1. **Никакого хардкода «июль 2026»**, никаких `if (campaign === 'renewal_july')`.
   Кампания — сущность: набор форм (из реестра) × набор детей (ростер/фильтр) × срок.
2. **Массовое обновление документов = штатный режим**, а не спецслучай. Один и тот же
   трекер обслуживает и продление, и онбординг нового клиента.
3. Состав кампании **выводится из реестра** (`expiryMonths`, `perInstance`, `condition`,
   `packets`), а не перечисляется руками.
4. Депersonalization уже требуется (center-lock + org-branding из настроек, `org` в
   реестре — Stage-2 swap point) — контур обязан её уважать.

**Коммерческий смысл:** «переход к нам не требует миграции данных — вы запускаете одну
кампанию, и через неделю ваш ростер в системе с актуальными подписанными документами».
Это снимает главное возражение при продаже. Контур строится под это с первого дня, а
не переделывается потом.

## 7. Ежегодный пересмотр — канон и замер (2026-07-28)

### 7.0 Предзаполнение прошлой формой НЕ отменяется

Вопрос владельца снят: renewal-форма открывается **предзаполненной** из прошлогодней записи,
письма родителям верны. Консервация образца подписи (2026-07-27) этому не мешает, а **служит**:
переносить старую подпись нечем, значит она рисуется заново.

### 7.1 КАНОН: предзаполнение несёт данные, но НИКОГДА подпись и её дату

Механизм уже построен (`prefill_tokens` / `mint_prefill_token` / `get_prefill`). Фиксируется,
что для renewal он **обязателен, а не опция**: данные переносятся, **подпись и дата рядом с ней —
никогда**. Пад открывается пустым, дата штампуется в момент росчерка.
Полная формулировка — [`docs/compliance/e-signature.md` §5b](../compliance/e-signature.md).

Запись, чья подпись унаследована, а не сделана, — не подписанная запись.

### 7.2 ⚠ Пересмотр — юридически ИНОЙ акт, чем первичное подписание

**OAC 5180:2-12-15** (бывш. 5101:2-12-15, перенумеровано 02.01.2025) требует при ежегодном
пересмотре DCY 01234 не полной подписи, а **ИНИЦИАЛОВ И ДАТЫ ОТ ДВУХ СТОРОН** — родителя
**и** администратора.

**Замер аффорданса инициалов, 28.07:**

| Где | Есть ли | Что именно |
|---|---|---|
| **Кит `DCY_01234_v8`** | ✅ **есть, и нужной формы** | три строки пересмотра × четыре поля: `pg_init_1..3` (инициалы родителя) · `pg_rev_1..3` (дата, `date:1` → штамп) · `adm_init_1..3` (инициалы администратора) · `adm_rev_1..3` (дата). Слово «INITIALS» в шапке колонки — из официального бланка |
| **Кит: тип поля** | ⚠️ | это обычные `t:'text'`, а не отдельный контрол инициалов. Гейт редакции уже есть (`f3b4c03`): на первичной подаче строки заперты + watermark, на renewal (`?t=`) открывается ПЕРВАЯ СВОБОДНАЯ. Недодел записан: без prefill'а строк по токену «первая свободная» всегда row 1 |

**Следствие:** сегодня контрподписать пересмотр из приложения можно только полной подписью
администратора — то есть совершить акт, отличный от того, который требует норма. Бумажный путь
(инициалы на том же листе) в приложении не воспроизводится.

### 7.3 ⚠ Указатель «что продлевает» — поля нет, и `supersedes_id` им быть не может

На бумаге пересматривают **ТОТ ЖЕ лист** и ставят на нём инициалы. Запечатанную запись править
нельзя → эквивалент = **НОВАЯ запись, предзаполненная из прошлой и несущая указатель на неё**.
Без указателя цепочка ежегодных пересмотров недоказуема.

**Замер:** указатель в таблице есть — `supersedes_id` (uuid, FK на саму таблицу, индекс
`where not null`) + `correction_reason`, с CHECK «есть указатель → обязана быть причина»
(`20260723_signature_trail.sql:40-64`). **Использование: 0 строк из 94.** `form_version` — тоже
0 из 94.

**Но это указатель ПРАВКИ, а не продления.** Он введён именно так, и текст seal-гарда говорит
это дословно: *«правка = новая строка (supersedes_id + correction_reason)»*. Продление —
не правка: прошлогодняя запись **не неверна**. Пустить renewal через `supersedes_id` значит
(а) требовать `correction_reason` у записи, которая ничего не исправляет, и (б) **слить в одно
ребро две разные цепочки** — «это исправляет то» и «это продлевает то», — после чего история
перестаёт различать исправленную запись и продлённую.

**Оценка:** нужен ОТДЕЛЬНЫЙ указатель. Два варианта:

| | Как | Плюс | Минус |
|---|---|---|---|
| **A** | новая колонка `renews_id` рядом с `supersedes_id` | ребро явное, старый CHECK не трогается | две почти одинаковые колонки |
| **B** | `prior_submission_id` + `relation` ∈ {`correction`,`renewal`} | одно ребро, тип отношения назван | миграция существующего `supersedes_id` (сегодня дёшево — 0 строк) |

Рекомендация — **B**, и именно **сейчас, пока обе колонки пусты**: 0 строк из 94 означает, что
переименование стоит одну миграцию и ноль бэкфилла. Через полгода это будет уже не так.

**Это одна работа с `form_version`, а не две.** Запись обязана знать **ЧТО** она продлевает
(указатель) и **КАКУЮ редакцию** подписали (`form_version`) — иначе цепочка пересмотров есть,
а доказать, по какому бланку каждый из них сделан, нельзя. Оба поля пусты у всех 94 записей,
оба заполняются только вперёд, бэкфилл невозможен по той же причине. Место — **заход 1**,
вместе с проводом.

### 7.4 ✅ ПРИМЕНЕНО 28.07 (миграция 20260728f): типизированное ребро + план миграции

**Читка обратно:** `supersedes_id` удалён; `prior_submission_id` + `relation` на месте с четырьмя
проверками (ребро и тип только вместе · словарь `correction|renewal` · причина обязательна ТОЛЬКО
для правки); текст seal-гарда переписан и больше не называет несуществующую колонку; провенанс
накрыт печатью наравне с содержимым. Проверено откатываемыми блоками — см. manual-entry спеку.

Принят вариант **B**: `prior_submission_id uuid` + `relation text CHECK (relation in ('correction','renewal'))`.
Делается **в заходе 1, одной работой с проводом `form_version`** — не двумя.

**Почему именно сейчас, а не «когда понадобится».** Использование сегодня = **0 строк из 94**.
Цена перехода растёт монотонно с каждой подписанной записью, а окно закрывается **тихо**: никто
не заметит дня, когда стало дорого. Через полгода это уже не одна миграция.

#### Судьба существующих колонок — ПЕРЕНОСИМ, не оставляем

`supersedes_id` и `correction_reason` (`20260723_signature_trail.sql:40-64`) — **0 строк**, значит
переезд бесплатен и бэкфилла нет:

1. `add column prior_submission_id uuid references menumaker.enrollment_submissions(id)`
   + `add column relation text`;
2. `check (prior_submission_id is null) = (relation is null)` — ребро без типа запрещено;
3. `check (relation is null or relation in ('correction','renewal'))`;
4. `check (relation <> 'correction' or nullif(btrim(correction_reason),'') is not null)` —
   **причина обязательна только для правки**. Продление причины не требует: оно ничего не исправляет;
5. `drop column supersedes_id` вместе со старым `enr_sub_correction_reason_ck` и индексом
   `enr_sub_supersedes_idx`; новый частичный индекс на `prior_submission_id where not null`;
6. `correction_reason` **остаётся** — она осмысленна и при новом ребре;
7. текст seal-гарда (`enrollment_submissions_seal_guard`) говорит дословно
   *«правка = новая строка (supersedes_id + correction_reason)»* — **обновить формулировку**,
   иначе сообщение будет называть колонку, которой нет.

Оставлять `supersedes_id` «помеченным устаревшим» — **отклонено**: две колонки под одно ребро
и есть тот способ, которым различие снова сотрут. Пустая колонка не заслуживает совместимости.

#### Правка ≠ продление — словами, чтобы через год не свели обратно

**Правка (`correction`)** говорит: *прежняя запись НЕВЕРНА*. Причина обязательна, потому что
кто-то утверждает про подписанный документ, что он содержит ошибку, и это утверждение само должно
быть подписано смыслом. Цепочка правок читается как «последняя версия истины».

**Продление (`renewal`)** говорит: *прежняя запись ВЕРНА и остаётся верной для своего года,
а вот запись следующего года*. Прошлогодний документ не отменяется и не исправляется — он
**закрывает свой период** и продолжает доказывать, что было подписано тогда. Цепочка продлений
читается как «история ежегодных пересмотров», и каждое звено в ней самостоятельно действительно.

**Почему нельзя одним ребром.** Если оба отношения ведут одной колонкой, то запрос «покажи
действующую редакцию» и запрос «покажи все пересмотры за три года» дают один и тот же список,
и различить в нём исправленную запись от продлённой уже нечем — а инспектору нужно ровно это:
не «сколько раз меняли», а «пересматривали ли ежегодно, как требует норма». Слитое ребро
превращает доказательство соблюдения нормы в доказательство того, что запись правили N раз.

## 7.6 Канон предзаполнения — три уточнения (Николай, 28.07)

Подтверждено: при ежегодном обновлении отдаём **редактируемую копию с удалённой подписью
и датой** (§7.1, e-signature §5b). Ниже — то, что иначе всплывёт багом в 2027.

### 7.6.1 Копия ≠ вернуть всё

Переносится **состояние ребёнка**. Не переносится **прошлогодняя сделка** — иначе родитель
увидит номер квитанции от платежа, которого в этом году не было.

| Форма | ПЕРЕНОСИТСЯ | НЕ ПЕРЕНОСИТСЯ |
|---|---|---|
| **`start_form`** (Registration & Fee Agreement) | имя ребёнка и DOB, дети 1..N, адрес, контакты родителей, «как узнали о нас», сиблинги, ожидается ли ребёнок, выбор варианта (`variant`) | **Check # · Receipt # · сумма принятого взноса · кто принял · отметки об оплате · `fees_applied` (снимок ставок прошлого года)** · обе подписи и их даты · слот администрации |
| **`enroll`** (CACFP Enrollment) | имя, DOB, адрес, родитель и контакты, расписание (дни и часы), классная комната | подпись родителя и `f_sig_date` · `calcExp` (срок, считаемый от подписи) |
| **`iea`** (Income Eligibility) | состав домохозяйства, дети, адрес, телефон, **race/ethnicity** | доход и суммы · подпись взрослого и её дата · **вся спонсорская секция** (F/R/P, дата определения, подпись спонсора) |
| **`dcy_01234`** | см. §7.6.3 — механика другая | **строки пересмотра `pg_init/pg_rev/adm_init/adm_rev`** (основание — §7.6.4) |
| **`child_release_authorization`** | список лиц с правом забирать, родство | подпись и дата · `media_consent` (согласие даётся заново) |
| **`parent_consent`, `parents_book_ack`, `staff_consent`** | имя подписанта | подпись, дата, версия согласия — это акт, он совершается заново целиком |

Правило одной строкой: **переносится то, что описывает РЕБЁНКА; не переносится то, что
описывает ПРОШЛОГОДНЕЕ СОБЫТИЕ** (платёж, подпись, определение, согласие).

### 7.6.2 «Копия» верна как опыт, неверна как модель

Запечатанную запись править нельзя. Создаётся **НОВАЯ** запись, предзаполненная из прошлой
и связанная ребром `relation='renewal'` (построено этапом А).

**Формулировки в UI и спеке писать так, чтобы «копия» нельзя было прочитать как «правим
старую».** Не «edit last year's form», а «this year's form, pre-filled from last year».

### 7.6.3 Различие по типам форм — два разных юридических акта

- **CACFP enrollment, IEA** — ежегодно **подписывают заново**: предзаполненная копия, подпись
  очищена, ставится новая.
- **DCY 01234** — **пересматривают инициалами**: механика в §7.6.4.

### 7.6.4 DCY 01234 — лист это ВИД, записи это ЦЕПЬ

Владелец: загружается **оригинал** для дополнительного проставления инициалов — тот же лист,
как на бумаге, три строки на три года. Не копия.

⚠ **Тензия:** запечатанную запись править нельзя (forward-only, `content_hash` заморожен) —
«дописать в оригинал» буквально невозможно.

**Решение:**
- оригинал **отображается** из запечатанной записи;
- инициалы и дата ложатся в **НОВУЮ** запись `relation='renewal'`;
- экранный и **печатный** DCY 01234 **собирается обходом цепочки**: тело формы из первичной
  подачи, каждое продление добавляет свою строку пересмотра по порядку.

Для человека — один лист с тремя строками. Для базы — цепь неизменяемых записей. Печать не тронута.

**Следствие:** ребро `relation='renewal'` для этой формы — не бухгалтерия, а **несущая
конструкция**: без него трёхлетний лист нечем пересобрать. Ещё одно основание, почему оно
уехало этапом А, пока колонки были пусты.

⛔ **Альтернатива отвергнута, с причиной:** ослаблять печать «только для строк пересмотра»
**не делать**. Печать с исключением перестаёт быть печатью, и первое исключение станет
прецедентом для второго.

**Оценка (не стройка, срок июль 2027)** — сборщик листа из цепочки:
порядок строк · что при **прерванной** цепочке (продление есть, первичной подачи в системе нет) ·
что если продление сделано, а **администратор инициалы не поставил** (строка родителя есть,
строка администрации пуста — лист показывает половину пересмотра, и это надо показать честно,
а не достроить).

### 7.6.5 Признак «строки пересмотра, которые пересмотром не являются»

Сборщик листа 2027 обязан знать: **строка пересмотра, чья дата равна дате первичной подписи
записи, пересмотром НЕ является.** Пересмотр по определению позже подписания — годом позже,
а не в тот же день.

Формулировка по **признаку**, не по ребёнку: под неё сегодня попадает одна запись (все три
строки проставлены датой подписи, до появления гейта строк пересмотра), но проверять надо
условие, а не список имён.
